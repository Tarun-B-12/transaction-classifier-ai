# Assumptions and Limitations

This document records the assumptions made while building the project and the limitations of the results. It exists so that anyone reading the project understands exactly what the numbers do and do not mean.

## Data Assumptions

- The dataset is synthetic. It was generated by `src/generate_transactions.py` to simulate realistic merchant description messiness. It is not real customer data and contains no real personal information.
- The synthetic descriptions were designed to include common real-world noise: payment processor prefixes, store numbers, location codes, and inconsistent casing and spacing. They do not capture every form of messiness found in real bank data.
- Nine spend categories were defined for the project. Real transaction categorization schemes are often larger and more granular.
- Transaction amounts were generated within fixed per-category ranges. They are not modeled on real spending behavior and should not be read as a spending pattern.

## Method Assumptions

- The rule-based baseline uses a deliberately realistic, non-exhaustive keyword list. It reflects what a person would plausibly write without having seen every merchant. It is expected to miss transactions, and those misses are the gap the LLM is measured against.
- The test set was hand-labeled by reading descriptions only. Where a hand label disagreed with the generator label, an adjudication pass set the final ground-truth label.
- The LLM classifier used a small, low-cost model and processed transactions in batches of 20 per API call.

## Limitations of the Results

- The 95.3 percent LLM accuracy reflects performance on clean synthetic merchant strings. On real bank transaction data, which is messier and more varied, accuracy would likely be lower.
- Of the 7 LLM misclassifications, 6 were a single ambiguous merchant, Uber Eats. Uber Eats can reasonably be classified as Transport or Restaurants. The ground truth was set to Transport, so the LLM's choice of Restaurants counted as incorrect even though it is defensible. This single ambiguity is the main reason Transport accuracy is lower than other categories.
- The 150-transaction test sample contains only 6 Coffee transactions, the result of random sampling variation. Coffee accuracy is therefore based on a small number of cases and should be read with that in mind.
- The test set is 150 transactions. A larger test set would give more stable per-category numbers.
- All metrics are project-level and dataset-level. They do not represent real-world company performance.

## What Would Improve This in a Production Setting

- A larger and more varied test set, ideally based on real, de-identified transaction data.
- A more granular category scheme matched to a specific business need.
- A confidence score on each LLM prediction, so low-confidence transactions can be flagged for human review.
- Monitoring of accuracy and cost over time as transaction patterns change.
